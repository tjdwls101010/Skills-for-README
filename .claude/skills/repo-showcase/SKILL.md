# repo-showcase

가치 있는 프로젝트가 방문자에게 그 가치를 첫 화면에서 전달하지 못하는 문제를 고친다. 대상은 소유자가 지목한 레포 하나(로컬 경로 또는 `owner/repo`)다.

**이 스킬이 아는 것의 한계를 먼저 말한다.** 근거는 README 97개(현재 73개 + 초기 고전 도구 12개의 3·9개월 스냅샷 24개)의 실측이고, 방문자 전환 데이터가 아니다. 별 수는 노출·명성·시간이 섞인 값이고, 종단 연구는 오히려 **인기가 문서 작업을 부르는** 역방향을 보고한다. 그래서 여기서 나오는 것은 "이렇게 하면 별이 는다"가 아니라 **"방문자가 문서만으로 판단할 수 있는가"**다. 소유자에게 성장을 약속하지 않는다.

## 방문자가 첫 화면에서 묻는 세 가지

| 질문 | 관찰 가능한 답 |
|---|---|
| 이게 뭔가 | 제품 범주, 다루는 입력, 만들어내는 결과. 방문자가 자기 말로 다시 말할 수 있어야 한다 |
| 나한테 맞나 | 대표 작업 하나, 그리고 **맞지 않는 조건**. 요구하는 계정·비용·권한이 여기 들어간다 |
| 어떻게 써보나 | 전제조건 → 최소 명령 → **예상 결과**. 설치 완료가 아니라 첫 성공까지다 |

**"첫 화면"은 제목부터 첫 번째 `##` 헤딩 직전까지의 도입 블록이다.** 줄 수가 아니라 구조로 정한다 — 방문자가 스크롤하기 전에 읽는 덩어리이고, 렌더링에서 눈으로 확인할 수 있다. 세 질문의 답이 그 안에 있으면 되고, 상세(플랫폼별 설치, 옵션, 설정)는 그 아래나 별도 문서로 보낸다.

"60초 안에" 같은 시간 목표를 쓰지 않는다. 설치가 무거운 프로젝트는 실행 전에 판단할 재료(결과 이미지, 출력 예시, 온라인 체험)를 주면 된다.

## 두 묶음을 섞지 않는다

**채택을 막는 결손**이 먼저다. 라이선스 부재·표기 불일치, 전제조건·권한·비용 미표기, 외부인이 재현할 수 없는 시작 경로, README 안의 모순. 이것들은 **소개가 아무리 좋아도 방문자를 돌려보낸다.** 알려진 평판이 없는 레포에서는 이 불확실성을 대신 해소해 줄 것이 없다.

**설득력 개선**은 그다음이다. 한 줄 정의, 결과 증거, description·topics, 데모. 결손이 남아 있으면 이쪽을 아무리 다듬어도 읽히지 않는다.

`scripts/audit_repo.py`가 이 두 묶음을 근거 줄 번호와 함께 낸다. **점수는 내지 않는다** — 구조 지표는 개선 전후 비교에만 쓴다.

## 절차

플래그는 여기 옮겨 적지 않는다. 각 스크립트의 `--help`가 계약이다.

**0. 대상과 경계를 정한다.** 대상 레포를 확인한다. **원격 쓰기(`gh repo edit`, push, PR)는 소유자가 그 단계에서 명시적으로 승인했을 때만 한다.** 스킬은 명령을 제시하고, 실행 여부는 소유자가 정한다.

**1. audit.** `python3 <스킬>/scripts/audit_repo.py <대상>` — 결손 / 개선 두 묶음. 상태값 넷을 구분해서 읽는다(`--help`에 정의). `lookup_failed`를 "없음"으로 옮기지 않는다. 코드와 README로 알 수 있는 것은 여기서 끝내고, **여기서 답이 나온 것은 소유자에게 묻지 않는다.**

**README가 아직 없으면** audit은 그대로 돌고 README에서 오는 항목만 `absent`로 나온다. 그때는 레포 자체에서 재료를 모은다 — 패키지 선언(`package.json`·`pyproject.toml`·`Cargo.toml`)의 이름·설명·엔트리포인트, `examples/`·`tests/`의 실제 입력과 출력, CLI의 `--help`, 그리고 커밋 메시지에 남은 의도. **여기서 모은 것은 재료이지 확정된 사실이 아니다** — 4단계에서 소유자에게 확인받는다.

**2. 진입 경로를 잠정 판정한다.** `references/trial-paths.md`에서 **해당하는 절 하나만** 읽는다. 판정 기준과 분기 규칙은 그 파일에 있다. **잠정이다** — 소유자가 4단계에서 "보증할 수 있는 첫 체험 경로"를 다르게 답하면 그 답이 이긴다. 그때는 해당 절을 다시 읽는다.

**3. 유사 프로젝트를 찾는다.** `scripts/similar_repos.py`로 후보 표를 만들고, 소유자가 1~3개를 고른다(직접 지목해도 된다). 고른 레포는 `audit_repo.py --compare`로 다시 조회한다. 이 레포들은 topics·어휘 정렬, 비교표, 한 줄 정의의 앵커, 그리고 8단계 PR 후보에 쓰인다.

**4. 소유자 인터뷰.** 아래 로스터. **한 번에 한 결정**으로 `AskUserQuestion`을 쓴다.

**5. 한 줄 정의 후보 3개를 만들어 고르게 한다.** 방문자가 아는 작업·도구·유사 레포에 연결한다. 초기 고전의 중앙값은 62자이고, 저관심 레포는 138자다. 길이 자체가 규칙은 아니지만 **긴 정의는 대개 자기 어휘로 자기를 설명하고 있다는 신호다.**

**5.5. 작성 개요를 한 장으로 확정한다.** 인터뷰 답과 audit 결과를 README 설계로 합치는 단계다. 이걸 건너뛰면 답은 다 있는데 무엇을 앞세울지 정하지 못한 채 쓰기 시작하게 된다. 소유자에게 이 개요를 보여 주고 시작한다.

| 칸 | 어디서 오는가 |
|---|---|
| 대상 독자 | 인터뷰 "가장 먼저 설득할 사용자" |
| 방문자가 할 대표 작업 하나 | 인터뷰 "없애려던 반복 작업" |
| 첫 화면이 유도할 행동 | 인터뷰 "최우선 목적" — 사용 확대면 체험, 기여 모집이면 기여 경로, 포트폴리오면 결과 설명이 첫 화면의 마지막 요소가 된다 |
| 첫 화면에 올릴 제약 | 인터뷰 "요구하는 권한·비용·계정" 중 **도입을 막을 수 있는 것만** |
| 쓸 결과 증거와 그 매체 | audit의 `result_evidence` + 아래 6단계 |
| 주 진입 경로 | 2단계 판정을 인터뷰 답으로 확정한 것 |
| **쓰지 않을 주장** | 인터뷰 "약속하지 않을 것" + audit이 근거를 찾지 못한 기존 문장 |

**6. README를 쓴다.** `references/first-visit.md`.

첫 화면 아래의 배치 기준 하나: **첫 성공에 필요한 것은 본문에, 첫 성공 이후에 반복해서 찾아볼 것은 이름 붙인 링크로** 보낸다. 플랫폼별 설치 표, 옵션 전체, 설정 파일 레퍼런스, 기여 절차가 후자다. 링크에는 "자세히"가 아니라 무엇이 있는지 쓴다.

**7. 메타데이터·커뮤니티 파일·신호.** `references/beyond-readme.md`.

**8. `LAUNCH-KIT.md`를 만든다.** `references/beyond-readme.md`의 마지막 절. 밖에 알릴 때 그대로 복사해 쓸 글감이다. **게시와 PR은 소유자가 한다.**

**9. 재audit과 검증.** `audit_repo.py`를 다시 돌려 결손이 실제로 줄었는지 본다. 그리고 지표가 검증하지 못하는 것을 따로 확인한다 — **설치 명령을 실제로 실행**하고, 링크를 열어 보고, README의 주장마다 레포 안의 근거를 대응시키고(`주장 → 파일:줄`), 라이선스 표기가 감지값·배지·본문·파일에서 모두 일치하는지 본다. 구조 지표는 **비퇴행 확인용**이지 합격 판정이 아니다.

## 소유자 인터뷰 로스터

audit과 탐색으로 답이 나온 것은 건너뛴다. 아래는 **코드만 봐서는 확정할 수 없는 의도와 약속**이다. 각 질문의 선택지는 "그걸 고르면 문서의 무엇이 달라지는지"를 담는다.

| 물을 것 | 선택지 모양 | 답이 바꾸는 것 |
|---|---|---|
| 이번 공개의 최우선 목적 | 사용 확대 / 기여 모집 / 포트폴리오·이력 | 첫 화면이 유도하는 행동(체험·기여·설명) |
| 가장 먼저 설득할 사용자 | 기존 대체재 사용자 / 이 분야 초보 / 시스템 통합자 | 비교 기준과 용어의 깊이 |
| 없애려던 반복 작업 하나 | audit에서 뽑은 후보 2~3개 + 직접 입력 | 한 줄 정의와 두 문장 피치의 주어 |
| 대체재보다 낫다고 **책임질** 차이 | 사용 단계 수 / 결과 품질 / 속도 / 통제·비용 | 비교표에 쓸 축과 공개 가능한 근거 |
| 보증할 수 있는 첫 체험 경로 | 무계정 데모 / 로컬 설치 / 계정·관리자 준비 필요 | 추천 경로와 첫 화면의 사전 고지 |
| 요구하는 권한·비용·계정 | 없음 / 계정 필요 / 유료 API / 관리자 승인 | 결손 판정의 `prereq_unstated` 해소 방식 |
| **약속하지 않을 것** | 하위 호환 / 성능 수치 / 특정 플랫폼 지원 / 없음 | 과장 제거 대상. 지금 못 지킬 약속을 문서에서 뺀다 |
| 지원 의무의 범위 | 실험·무보장 / 최선 노력 / 명시된 버전·기간 | 현재 상태 문구와 SECURITY의 지원 버전 |
| 실제로 받을 기여 | 버그만 / 합의된 기능 / 폭넓은 확장 / 받지 않음 | CONTRIBUTING의 범위. 받지 않을 것을 적는 편이 거절보다 낫다 |
| 코드·문서·이미지의 권리 확보 | 전부 확인 / 제3자 자료 포함 / 미확인 | 라이선스 선택과 공개 보류 대상 |
| 가장 가까운 대안 레포 | 3단계의 후보 표 + 직접 입력 + "없음" | 비교표, 한 줄 정의의 앵커, PR 후보 |

**"약속하지 않을 것"을 반드시 묻는다.** 나머지 열 개는 무엇을 쓸지 정하고, 이 하나가 무엇을 지울지 정한다. 소유자는 자기 프로젝트를 과장하는 쪽으로 기울고, 지키지 못한 약속 하나가 문서 전체의 신뢰를 멈춘다.

## 경계

- **원격을 바꾸는 것은 전부 승인 후.** `gh repo edit`, push, PR 생성. 명령을 보여 주고 소유자가 실행하거나 승인한다.
- **범위 밖**: 커뮤니티·SNS 채널 안내와 게시 자동화, 스타게이저·기여자에게 보내는 개인 연락. 플랫폼 약관과 개인정보 보호 규정에 어긋나고 평판에 역효과다. 스타게이저·기여자 목록은 조회하지도 않는다. 스킬은 **게시물 재료까지** 만들고 게시하지 않는다.
- **기존 파일을 덮어쓰지 않는다.** `scripts/scaffold_community.py`는 이미 있는 LICENSE·CONTRIBUTING·SECURITY·CODE_OF_CONDUCT를 보면 **아무것도 쓰지 않고** 종료한다(요청한 파일이 여럿이어도 전부 쓰지 않는다). `--force`가 있지만 **소유자가 기존 내용을 읽고 버리기로 한 뒤에만** 쓴다. README를 고칠 때도 **기존 사실은 보존하고**, 확인되지 않은 주장만 뺀다.
- **소유자가 확인해 주지 않은 것을 쓰지 않는다.** 성능 수치, 지원 약속, 로드맵. 모르면 비워 두고 물어본다.
