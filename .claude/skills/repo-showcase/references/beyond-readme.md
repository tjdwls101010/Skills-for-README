# README 밖 — 메타데이터, 커뮤니티 파일, 소개 재료

메타데이터·신호를 다루는 호출과 `LAUNCH-KIT.md`를 만드는 호출에서 읽는다.

**여기 있는 것들의 효과는 README보다 약하고, 근거도 약하다.** GitHub 문서가 설명하는 것은 이 기능들의 **노출·분류 효과**이지 전환 효과가 아니다. 결손(라이선스)이 아닌 항목은 README를 고친 뒤에 손댄다.

## description — 137자에서 잘린다

**검색 결과에서 137자를 넘으면 137번째 글자에서 잘리고 `…`이 붙는다. 단어 경계를 지키지 않는다.** `Local first, OCI compatible, pure R…` 처럼 끊긴다. 연속 공백은 먼저 하나로 접힌다. 프로필의 Repositories 탭은 전문을 보여 주므로, 137자는 **상한이 아니라 "검색으로 발견될 때 읽히는 길이"**다.

그래서 규칙은 "짧게 써라"가 아니라 **"앞 137자 안에 정체성이 끝나야 한다"**이다. 뒤에 붙는 문장은 검색에서 보이지 않아도 되는 것만.

측정된 계층 중앙값: 인기 프레임워크 61자, 고전 CLI 48자, 상승 레포 87자, **별 0~4개 레포 126자(20개 중 8개가 잘린다)**.

description은 README의 한 줄 정의와 **같은 것을 말하되 같은 문장일 필요는 없다.** 한 줄 정의는 방문자가 이미 레포 안에 있을 때 읽고, description은 목록에서 이 레포를 열지 말지 정할 때 읽는다.

## topics — 분류 경로

유사 레포의 topics와 겹치게 맞춘다. `audit_repo.py --compare`의 `missing_topics`가 후보다. **개수 목표는 없다** — vue는 topics가 0개다. 채우는 이유는 그 topic 페이지를 통해 들어오는 경로 하나를 여는 것뿐이다.

## homepage

문서 사이트나 온라인 체험이 있으면 채운다. 없으면 비워 둔다. 저장소 자신을 가리키게 두지 않는다.

## 적용

```bash
gh repo edit OWNER/REPO --description "..." --add-topic a,b,c --homepage URL
```

**이것은 원격을 바꾼다. 명령을 보여 주고 소유자의 승인을 받은 뒤에 실행한다.**

## LICENSE — 유일하게 결손인 항목

라이선스가 없으면 방문자는 **쓸 수 있는지 자체를 모른다.** 소개가 아무리 좋아도 여기서 멈춘다.

`scripts/scaffold_community.py --file license --license <선택>` 로 정본을 그대로 만든다. **라이선스는 소유자가 고른다** — 스크립트도 이 스킬도 대신 정하지 않는다. 인터뷰의 "권리 확보" 답이 미확인이면 먼저 그것부터 정리한다.

**표기 일치를 네 곳에서 확인한다**: GitHub 감지값, 배지, README 본문, 파일 자체. 흔한 어긋남 두 가지 —

- 파일은 있는데 감지값이 `NOASSERTION`인 경우(jq). 본문이 "코드는 MIT, 문서는 CC BY 3.0"처럼 나눠 쓰고 있을 수 있다. 이건 결손이 아니라 **본문 설명이 필요한 상태**다.
- 본문은 MIT라고 쓰는데 파일이 없는 경우. **둘 중 무엇이 사실인지 소유자에게 확인한다.** 파일을 임의로 만들면 없던 권리 관계를 만들어 내는 것이 된다.

## CONTRIBUTING · SECURITY · CODE_OF_CONDUCT — 조건부

빈도만 보면 이것들은 인기와 무관하다(SECURITY는 인기 레포도 절반 이하, CoC는 1인 프로젝트에 대부분 없다). **조건이 맞을 때만 만든다.**

| 파일 | 만드는 조건 | 비어 있으면 안 되는 칸 |
|---|---|---|
| CONTRIBUTING | 인터뷰에서 기여를 "받는다"고 답했을 때 | **받지 않을 것**. 거절보다 기여자의 시간을 아낀다 |
| SECURITY | 실행 권한·비밀정보·네트워크를 다루는 도구일 때 | 신고 창구와 지원 버전. 대응할 수 없는 범위를 적지 않는다 |
| CODE_OF_CONDUCT | 여러 사람이 참여하는 공간이 이미 있을 때(이슈·디스커션이 도는 상태) | 신고 연락처. **창구 없는 CoC는 지킬 수 없는 약속이다** |

`scaffold_community.py`는 연락처(`--contact`)가 없으면 자리표시자를 남기고 경고한다. **자리표시자가 남은 채로 커밋하지 않는다.**

## Releases · 소셜 미리보기 · 프로필

셋 다 제안하고 소유자가 정한다.

- **Releases**: 버전이 있는 도구는 태그와 릴리스 노트가 "지금 살아 있는 프로젝트"의 신호다. 첫 릴리스는 `v0.1.0`으로 충분하고, 노트에는 **이 버전으로 무엇을 할 수 있는지**를 쓴다.
- **소셜 미리보기**: 링크가 공유될 때 뜨는 이미지. 없으면 GitHub이 자동 생성한 카드가 뜬다(그것도 나쁘지 않다). 데모 GIF의 대표 프레임이 좋은 후보다.
- **프로필 README와 핀 레포**: 소유자 계정에 도구가 여러 개면, 프로필에서 이 레포로 가는 경로를 만든다. 핀 6개는 계정 방문자에게 "이 사람이 무엇을 만드는가"의 답이다.

## LAUNCH-KIT.md

밖에 알릴 때 **그대로 복사해 쓸 글감**이다. 게시는 소유자가 한다. 이 파일은 저장소에 커밋하지 않는 편이 낫다 — 방문자에게 보여 줄 문서가 아니다. `.gitignore`에 넣거나 소유자에게 위치를 확인한다.

구성:

1. **한 줄 정의** — README와 같은 문장.
2. **두 문장 피치** — 첫 문장은 *누구의 어떤 반복 작업을 무엇으로 바꾸는지*, 둘째 문장은 *가장 가까운 대안과의 차이와 그 조건*. 인터뷰의 "책임질 차이" 답에서 나온다.
3. **데모 GIF 경로** — 만들었으면 파일 경로, 안 만들었으면 만드는 명령.
4. **Show HN 형식 제목 후보 2~3개** — `Show HN: <이름> – <한 줄 정의>`. 대시 뒤가 제목의 전부다. 과장 표현과 이모지를 넣지 않는다.
5. **제출 조건** — 해당하면 스킬 마켓플레이스나 awesome 목록의 제출 요건(라이선스, 최소 문서, 형식). 요건을 못 채운 상태로 제출하지 않는다.
6. **"Similar projects" PR 후보** — 인터뷰의 "가장 가까운 대안" 답과 `--compare` 결과 중, README에 그런 절이 **이미 있는** 레포만. 없는 레포에 절을 새로 만들자고 PR을 보내는 것은 다른 종류의 요청이다.

**만들지 않는 것**: 스타게이저·기여자에게 보내는 개인 연락(이메일·DM). 플랫폼 약관과 개인정보 보호 규정에 어긋나고, 받는 쪽에서 스팸으로 읽혀 평판에 역효과다. 그 목록은 조회하지도 않는다.
