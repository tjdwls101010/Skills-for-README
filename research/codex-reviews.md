# 코덱스 리뷰 레인 — 결과와 채택/기각

`repo-showcase` 스킬의 계획과 코퍼스를 GPT(코덱스)에 두 번 걸었다. 원 응답 전문은 `.tmp/codex-runs/`(gitignored)에 있고, 여기에는 **무엇을 지적받았고 무엇을 어떻게 반영했는지**만 남긴다. 반영 위치가 적혀 있지 않은 항목은 반영하지 않은 것이다.

## 레인 1 — 계획 비판 (2026-09-08, `plan-critique`)

계획 초안만 주고 "가장 큰 결함부터"를 요구했다. 코덱스가 짚은 핵심은 **인기 레포에서 자주 보이는 형식을 무명 레포의 설득 원인으로 취급할 위험**이었다.

## 레인 2 — 코퍼스 종합 (2026-09-08, `corpus-synthesis`)

README 원문 30개 버전 + 가이드 19편을 코덱스가 전문으로 읽고 원칙을 도출하게 했다. **내 목록에 없었는데 코덱스가 근거와 함께 가져온 것**만 아래에 적는다. 나머지(첫 화면의 한 줄 정의, 결과 증거, 대안 연결)는 내 실측과 겹쳤다.

1. **설치 완료가 아니라 첫 성공까지의 경로.** `llm` m3 L15–51은 설치→키 저장→질문→실제 출력까지 이어진다. → `first-visit.md`, `trial-paths.md`의 "예상 결과" 요소.
2. **필수/선택 전제조건 분리, 도입을 막는 조건은 첫 화면에.** `mcp-ms-loop`는 인증·Node를 L3–10에 쓰지만 도입을 막는 M365 관리자 권한은 L58–65에 있다. → `blockers.py`의 `prereq_unstated`.
3. **비교는 조건과 손해까지.** `fd` m3 L37–60은 약 100만 파일·동일 결과 14,030개라는 조건을 밝히고 "`find -iname`이면 속도가 비슷하다"까지 쓴다. 반례로 `autoharness` L13의 42%→78%는 외부 연구 수치다. → `first-visit.md` 비교표 규칙: 인용 수치를 제품 성능으로 옮기지 않는다.
4. **분기는 프로젝트 유형이 아니라 진입 경로.** Excalidraw는 웹앱이자 라이브러리, MarkItDown은 CLI이자 라이브러리다. 유형별 템플릿은 중복을 만든다. → `trial-paths.md`를 5개 진입 경로(온라인 체험 / CLI 설치 / import 라이브러리 / 호스트 플러그인 / 관리자 설정형 통합)로 구성.
5. **현재 상태·지원 범위가 홍보보다 먼저.** `rye` 현재 L16–22는 개발 중단과 uv 이전 경로를 앞세운다. 반례로 `mcp-re` L58–64와 L107–112가 서로 모순되고, `autoflow`는 L110–116의 사용 예제를 L166–167에서 예정 기능이라 한다. **풍부한 문서도 모순 하나로 판단을 멈추게 한다.** → `blockers.py`의 `status_contradiction`, 9단계 주장-근거 대응표.
6. **라이선스는 감지값·배지·본문·파일 네 곳의 일치를 확인.** `jq`는 감지값 `NOASSERTION`이지만 본문 L73–78에서 코드 MIT·문서 CC BY 3.0·포함 코드 ICU를 구분한다. 반대로 `vibe-toolkit` L167–169는 MIT라고 쓰지만 파일이 감지되지 않는다. → `blockers.py`의 `license_missing` / `license_mismatch`.
7. **소유자 인터뷰 8문항**(목적 / 첫 설득 대상 / 없애려던 반복 작업 / 책임질 차이 / 보증 가능한 첫 체험 경로 / 지원 의무 / 받을 기여 / 권리 확보). → SKILL.md 로스터의 골격. 여기에 내가 3문항을 더했다: "약속하지 않을 것", "요구 권한·비용·계정", "가장 가까운 대안 레포".
8. **가이드 통념 중 코퍼스가 뒷받침하지 않는 것** — Standard README의 120자 미만·100줄 이상 TOC 필수·고정 섹션 순서, Make a README의 "짧기보다 긴 편이 낫다", Best-README-Template의 배지·로고·기술 스택 순서, RDD, "커뮤니티 파일·소셜 미리보기가 성장시킨다". → `first-visit.md`의 "따르지 않는 규칙" 절.

### 코덱스가 발견한 지표 스크립트 버그 2건

수집 단계의 지표 스크립트가 (a) 한국어 헤딩("설치")을 설치 헤딩으로 세지 못했고(Ultra-Search), (b) Mermaid 펜스를 첫 코드 블록으로 셌다(autoflow). 2단계에서 `readme_metrics.py`에 다국어 헤딩 사전과 Mermaid 제외를 넣어 수정하고, 수정 전후 표를 `metrics-summary.md`에 함께 싣는다.

### 기각한 것

- **`owner-interview.md` 별도 파일** (레인 2의 E 제안). 인터뷰 로스터는 **모든 호출에서 읽힌다.** 매번 읽는 것을 참조 파일로 빼면 분할이 아니라 왕복이 된다. SKILL.md 본문에 둔다.
- **`metadata-community.md`라는 이름** (레인 2의 E 제안). 같은 내용을 `beyond-readme.md`로 부른다. 이 파일이 답하는 질문은 "커뮤니티 파일이 무엇인가"가 아니라 "README 밖에서 무엇을 더 할 수 있는가"이고, 파일 이름이 그 호출 조건을 그대로 말하는 편이 낫다.
- **프로젝트 유형별 완전한 템플릿.** 레인 2가 직접 반박했다(4번).

## 부록 — description 잘림 기준 실측 (2026-09-08)

계획의 미해결 항목이었다. **직접 측정해 확정했다.**

측정 방법: 코퍼스 73개 중 description이 120자를 넘는 레포에 대해 GitHub 검색 결과의 JSON 페이로드(`hl_trunc_description`)를 받아 원본과 대조했다.

```
curl -sL 'https://github.com/search?q=repo%3A<owner>/<repo>&type=repositories' \
  -H 'Accept: application/json' \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['payload']['blackbirdSearchRoute']['results'][0]['hl_trunc_description'])"
```

결과 (8개 응답 수집, 나머지는 연속 요청 제한으로 실패):

| 레포 | 원본(공백 정규화 후) | 표시 | 잘림 |
|---|---|---|---|
| jo-inc/camofox-browser | 135 | 135 | 아니오 |
| httpie/cli | 137 | 137 | 아니오 |
| arcboxlabs/arcbox | 141 | 137 + `…` | 예 |
| affaan-m/ECC | 171 | 137 + `…` | 예 |
| mksglu/context-mode | 171 | 137 + `…` | 예 |
| tjdwls101010/Codex-in-Claude | 178 | 137 + `…` | 예 |
| headroomlabs-ai/headroom | 185 | 137 + `…` | 예 |
| coldteadotai/pr-lens | 206 | 137 + `…` | 예 |

**확정된 규칙**: 연속 공백을 하나로 접은 뒤 **137자를 넘으면 137자에서 자르고 `…`을 붙인다. 단어 경계를 지키지 않는다** — `pure R…`, `thread resume, a…`처럼 단어 중간에서 끊긴다. 잘린 6개 모두 `원본[:137] + '…'`와 정확히 일치했다.

**적용 범위 주의**: 이 잘림은 **검색 결과 목록에만** 있다. 프로필의 Repositories 탭은 같은 description을 통째로 보여준다(`redhat-et/ripwire`의 325자가 잘리지 않고 전부 나온다 — `<p itemprop="description">`에 line-clamp 없음). 즉 137자는 "description의 최대 길이"가 아니라 **"검색으로 발견될 때 읽히는 길이"**다. 스킬은 이 숫자를 상한이 아니라 **앞 137자 안에 정체성이 끝나야 한다**는 배치 규칙으로 쓴다.

원자료: `.tmp/description_truncation.json`.
